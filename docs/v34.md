# V.34 / V.90 / V.92 — implementation status and engineering report

Authority: ITU-T V.34, V.90, V.92. Reference implementation in the tree:
spanDSP `v34tx.c`, `v34rx.c`, `v34_logging.c`, `v34_tables.h`,
`v34_superconstellation_map.h` (LGPL 2.1), extended by
`third_party/spandsp/src/spandsp-v34-phase3.patch` (this project).

## Executive summary

The spanDSP V.34 engine has been made to build and run in this repository and
has been extended so that a full loopback call now completes:

```
V.8 -> V.34 phase 1 -> phase 2 (INFO0, A/B tones, INFO1, L1/L2 probing)
    -> phase 3 (S/!S, PP, TRN, J, J')
    -> phase 4 (second TRN, MP/MPH exchange, MP', E)
```

All of these transitions are driven by decoded signals (coherent signal
detection and CRC-checked messages), not by timers or energy heuristics.

What is verified:

1. **Mapping engine (bit-exact).** `v34_mapping` round-trips data bits
   through two modem contexts (S/Q/I parsing, superframe structure, shell
   mapping, differential encoding, trellis/precoding, scrambling and the
   inverse demapper) with **0 mismatches at 4800, 9600, 19200 bps (2400 baud),
   16800 (2743), 21600 (2800), 24000 (3000), 28800 (3200) and 33600 bps
   (3429)**.

2. **Full start-up and control exchange (loopback).** `v34_loopback` shows
   V.8 negotiation, phase-1 INFO0 exchange, A/B tone sequencing, phase-2
   INFO1c/INFO1a exchange with correct parameters, L1/L2 line-probe DFT, the
   S/!S alignment, PP/TRN training, J/J', the post-J TRN, the MP/MPH exchange
   ("Rx MP:", "far MP received, sending MP'", "MP' sent twice, sending E",
   "e_baud_init") on both sides.

The transmit side is also complete: after the E sequence both modems enter
the primary-channel data mode (`Tx - data_baud_init`, stage DATA) and send
data symbols from the verified mapping engine.

The remaining blocker for a V.34 data connection is the **primary-channel
receiver**: `process_primary_half_baud()` is a disabled shell that still
refers to an older (v22bis-style) architecture, so the receivers stay in the
control-channel mode after E and no data bits are decoded.

## What was implemented in this tree

- `build_v34.sh` generates every table with spanDSP's own generators (RRC
  sets, shell map, trellis coders, probe signals, pre-emphasis with the
  vendored meteor engine) and builds `libsmv34.a`; leftover per-sample debug
  printfs are suppressed by `spandsp-v34-debug-printfs.patch`.
- `spandsp-v34-phase3.patch` adds, over upstream:
  - **Phase-3 S detection** (`v34rx.c`): two coherent correlators, at the
    far end's V.34 carrier and at this side's control-channel carrier. On the
    real waveform the S signal presents as coherent V.34-carrier energy
    (normalised ratio ~0.3) with no control-channel tone; the phase-1 A/B
    tones present as a 0.707 ratio tone on the control-channel carrier and
    the PP/TRN training is incoherent. Three qualifying 10 ms blocks latch
    `V34_EVENT_S`.
  - **Transmit sequencing** (`v34tx.c`): the caller waits on the S event
    (staying on its baud generator so the event is re-checked), both sides
    transmit S/!S/PP/TRN, the caller sends J', the answerer leaves J for the
    post-J TRN, and the post-J TRN switches the receiver to the
    control-channel demodulator.
  - **MP/MPH completion**: sent on the control channel; when the far end's
    CRC-validated MP has been decoded it is acknowledged with MP', sent
    twice, then the E sequence begins.
  - New state fields in `spandsp/private/v34.h` (`s_signal_seen` and its
    correlator state, `trn_after_j`, `mp_tx_count`).

## Exact remaining blockers

1. **Data/constellation amplitude calibration** between the training
   sequence and the primary-channel data (the `35.77` factor in an upstream
   comment is the only hint; the V.34 text defines the actual transmit
   levels). The data generator currently emits one constellation unit as
   1.0, matching the Q9.7 mapping format.
2. **Primary-channel receiver.**
   `process_primary_half_baud()` (`v34rx.c`) is `#if 0` for the decode path
   and refers to `decode_baud()`/`s->constellation[]` from another modem
   implementation. A receiver must be written around the existing pieces:
   `pri_symbol_sync()` (timing), the equalizer buffers, carrier tracking,
   `viterbi_calculate_candidate_errors()`, `viterbi_calculate_branch_errors()`,
   `viterbi_update_path_metrics()`, `viterbi_trace_back()`,
   `precoder_rx_filter()` and the demap tail of `v34_put_mapping_frame()`.
3. **Level calibration** of the data constellation against the training
   sequence (the `35.77` factor in an upstream comment is the only hint; the
   V.34 text defines the actual transmit levels).
4. **V.90/V.92**: no engine exists anywhere; they sit above a working V.34
   data mode. The PCM transport (G.711/RTP in `sm_sip`) is ready.

## How to continue

1. Add `get_data_baud()` and the `E -> data` transition in `v34tx.c`,
   using `v34_get_mapping_frame()` per 8-baud frame.
2. Build the primary-channel receiver around the existing timing, equalizer
   and Viterbi pieces, then verify with `v34_loopback` (ideal channel) and
   add a channel model.
3. Only after data bits flow end to end, enable V.34 in the daemon's V.8
   capabilities (currently only V.22 is advertised, which keeps the working
   hardware path untouched).
