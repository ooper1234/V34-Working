# V.34 / V.90 / V.92 — implementation status and engineering report

Authority: ITU-T V.34, V.90, V.92. Reference implementation in the tree:
spanDSP `v34tx.c`, `v34rx.c`, `v34_logging.c`, `v34_tables.h`,
`v34_superconstellation_map.h` (LGPL 2.1).

## Executive summary

- A complete-looking but unfinished V.34 engine exists in spanDSP (6000+
  lines); it was previously dismissed. It has now been made to **build and
  run** in this repository, and it executes the V.8 start-up plus V.34
  **phases 1 and 2** to completion in a loopback harness.
- It **stalls at the phase 2/3 boundary** because the receiver side of the
  S/!S signal (phase 3 control channel) is not implemented: the event
  `V34_EVENT_S` is consumed by the transmitter but never generated by the
  receiver. The final data pump (`V34_RX_STAGE_PRIMARY_CHANNEL`) is stubbed
  (an explicit `TODO: start data reception`).
- There is **no V.90 or V.92 engine anywhere** (no code exists in spanDSP or
  elsewhere that we can use). V.90 requires the V.34 link first, so the
  blocker for V.90/V.92 is the unfinished V.34 engine, not the PCM transport.
- The digital PCM transport (G.711 over RTP in `sm_sip`) is not the issue and
  is ready to carry a PCM-downstream modem if/when one exists.

## What is implemented and verified now

Build: `src/modem/v34/build_v34.sh` builds `libsmv34.a` from the vendored
spanDSP sources, generating every table the sources need with spanDSP's own
generators:

- `make_modem_filter` — all V.34/V.22bis RRC filter sets
- `make_v34_shell_map` — shell-mapping tables
- `make_v34_convolutional_coders` — trellis encoder tables
- `make_v34_probe_signals` — line-probe signal table
- `make_v34_tx_pre_emphasis_filters` + `tools/meteor-engine.c` — pre-emphasis
  filters (the meteor filter-design engine, vendored)

Leftover per-sample debug `printf`s in upstream `v34rx.c`/`v34tx.c` are
suppressed by `spandsp-v34-debug-printfs.patch` (they destroyed throughput and
made logs unreadable; no functional change).

Test: `tests/v34_loopback.c` (built when the engine is present) connects a
calling and an answering modem directly, starting with V.8:

```
./v34_loopback 2400 4800 60
```

Verified state progression (real output):

```
[V8 caller] status=2 mods=0x800 cf=6 proto=1
[V8 answerer] status=2 mods=0x800 cf=6 proto=1
STAGES caller tx=INFO0 rx=INFO0 | answerer tx=INFO0 rx=INFO0
STAGES caller tx=FIRST_B rx=INFO0 | answerer tx=INIT_A rx=TONE_B
STAGES caller tx=B_INFO_SEEN rx=TONE_A | answerer tx=FIRST_NOT_A rx=TONE_B
STAGES caller tx=SECOND_B rx=TONE_A | answerer tx=POST_L2_A rx=TONE_B
STAGES caller tx=SECOND_B_WAIT rx=INFO1A | answerer tx=A_SILENCE rx=TONE_B
STAGES caller tx=INFO1 rx=INFO1A | answerer tx=INFO1 rx=INFO1C
STAGES caller tx=INFO1 rx=INFO1A | answerer tx=TRN rx=INFO1C
STAGES caller tx=INFO1 rx=INFO1A | answerer tx=J rx=INFO1C   <-- stall
```

Both sides decode each other's INFO0, the caller's INFO1c and the answerer's
INFO1a are parsed with correct contents (baud rate, carrier, power reduction,
pre-emphasis index), the caller performs the L1/L2 line-probing DFT (energy
exactly at the 21 probe frequencies, zero at the skipped bins), and the
answerer transmits S/!S, PP and TRN. The handshake then stalls.

## Exact remaining blockers (file and line references)

1. **S/!S detection missing (phase 3 entry).**
   `v34rx.c` never sets `V34_EVENT_S`; the only reference in the tree is the
   consumer in `v34tx.c:2367` (`V34_TX_STAGE_J`). The answerer therefore
   re-sends J forever waiting for the caller's S.
2. **Caller TX has no post-INFO1c path.**
   `v34tx.c` `get_info1_baud()` sends the calling party to
   `tx_silence_init(s, 30000)` after INFO1c and never resumes (no code waits
   for the answerer's S and then sends the caller's S/!S, MD, PP, TRN, J').
3. **Primary-channel receiver stubbed.**
   `V34_RX_STAGE_PRIMARY_CHANNEL` is defined but never entered; `v34rx.c:2045`
   carries `/* TODO: start data reception */`. The 4D trellis decoder, shell
   demapping, differential decoder and descrambler for the data path are not
   wired (the tables exist: `v34_superconstellation_map.h`,
   `v34_convolutional_coders.h`, `v34_shell_map.h`).
4. **MP/MPH completion.** TX-side MP/MPH generation exists
   (`mp_or_mph_baud_init`), but the phase-4 completion, E/B1 signalling and
   the switch to `current_get_bit`/data mode are missing.
5. Upstream (freeswitch/spandsp) is byte-identical to the vendored sources and
   is still marked "THIS IS A WORK IN PROGRESS - NOT YET FUNCTIONAL". There is
   no newer version to pull.

## What V.90/V.92 would additionally require

After a working V.34 phase 4:

1. V.90 MP exchange selecting the PCM downstream (V.34 `MP`/`MPH` already
   carry the modulation-type field; V.90 adds the PCM-modem parameters).
2. Digital Impairment Learning (DIL) and the digital-side PCM constellation
   mapping with precoding; the μ-law/A-law PCM domain is already available
   sample-exactly in `sm_sip` (RTP PCMU).
3. The V.90 upstream path (analog V.34-style at rates up to 33.6 kbit/s), and
   for V.92: PCM upstream, Quick Connect parameter storage and Modem-on-Hold.
4. A real interop effort against the hardware modem.

Because the V.90/V.92 layers do not exist in any usable open-source form,
they cannot be reached until the V.34 engine above is completed. Advertising
them before that would be dishonest and is not done: the daemon's V.8 JM
still advertises only V.22.

## How to continue

The measured, lowest-risk order of work is exactly the blocker list above:
implement `V34_EVENT_S` detection (tone-transition detector at the S baud
rate, setting the event and advancing the RX stage), then the caller's
S/!S/MD/PP/TRN/J' transmit path, then the primary-channel receiver and MP/MPH
completion. Each step can be verified with `v34_loopback` and then against the
hardware modem once the data mode is reached.
