# V.90 / V.92 — server-side architecture analysis

Authority: ITU-T V.90 (56 000 bit/s downstream PCM), V.92 (48 000 bit/s upstream,
Quick Connect, PCM upstream, modem-on-hold). Status: **ANALYSIS ONLY — NOT
IMPLEMENTABLE on this Asterisk analog path as true V.90.** This document states
exactly why, and what the correct fallback behaviour is.

## 1. V.90 server-side requirement

V.90 requires the answering DCE (the ISP modem bank side) to be a **digital-side**
device connected through a digital (PCM) bearer with a **known** codec mapping
(mu-law/A-law, sign bit pattern) from the terminal to the network. The downstream
56 000 bit/s rate exploits the ability to send a chosen sequence of PCM codewords
into the network; the client decodes the specific PCM levels into data.

The typical deployment: client analog modem → 2-wire PSTN → Class 5 switch (with
digital PCM) → PRI to ISP → V.90 server DCE that knows the G.711 codeword grid and
the network's digital loss plan.

## 2. Our intended backhaul — what it can and cannot provide

```
ATA  ->   G.711 mu-law   ->   Asterisk   ->  AudioSocket -> 8k linear PCM -> softmodem
```

- The ATA→Asterisk leg is an **analog terminal adapter to SIP** over a packet
  network (Internet/VoIP), then re-encoded in G.711 inside Asterisk, then g.711-to-
  linear in chan_audio_socket. This is NOT a deterministic digital PCM grid:
  - Packetization/reassembly adds jitter; samples are not phase-locked to any
    PCM network clock.
  - The ATA performs its own analog TX shaping; there is no guaranteed codeword
    mapping table available to the soft "server" side.
  - No knowledge of the network's digital loss/echo-cancel settings and no control
    of the individual PCM codewords sent toward the far network.
  - The upstream (client→us) is plain analog as in any V.90; the problem is the
    downstream (us→client), where V.90 requires sending exact PCM levels. We
    cannot generate those levels through the ATA/Internet/Asterisk path — the ATA
    will re-quantize whatever we send to its own mu-law representation, destroying
    the required level accuracy, and jitter destroys symbol timing.

Therefore: **genuine V.90 56 000 bit/s downstream is NOT achievable over a
G.711/AudioSocket/Asterisk path through an analog ATA.** Same for V.92's PCM
upstream and its signalling (Quick Connect / MOH use in-band digital signalling
that assumes the digital-side environment).

## 3. What remains possible

If the network path to the client is a **digital trunk (PRI/SIP to a carrier that
provides clear-channel or deterministic G.711 to an analog client)** and Asterisk
passes G.711 at 8 kHz linear with the codec mapping known and phase-locked, a
V.90-class service *might* be feasible but requires:
1. Read of the complete V.90/V.92 Recommendation (all Annexes).
2. A server-side control of exact PCM word sequences toward the client.
3. Loss/echo-cancel parameters and timing recovery from a real network clock.
4. A **real V.90 client modem** to validate.

None of that is present here, and we must not fake 56 kbit/s.

## 4. Correct answerer behaviour for V.90-flagging callers without V.90

Per the fallback hierarchy the answerer:

1. Never advertises V.90/V.92 availability in V.8 CM/JM availability bits
   (`pcm_modem_availability = 0`), matching the reference stack.
2. If a caller sends a V.90/V.92-oriented CM/JM, we select the highest
   mutually-supported **analog** modem (V.34, else V.32bis, ...):
   the standard's normal fallback when a digital-side DCE is unavailable.
3. This is a correct, standards-conformant V.8 procedure — not a downgrade hack:
   V.8 §8.2.3/8.6 define that a DCE indicates its PCM-modem availability in the
   availability octet; an unavailable bit simply means that mode is not selected.

## 5. Recommendation to the project

Implement V.34 correctly, then V.32bis; **do not** spend effort on V.90/V.92 DSP
until a deterministic digital-side backhaul exists. Keep the V.8 availability
octet wired to `0`. Document this decision in `call.json` when a V.90 CM arrives
("caller offered V.90; answerer fell back to V.34/V.32bis per unavailable PCM
modem bit").
